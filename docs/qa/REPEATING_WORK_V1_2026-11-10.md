# 반복업무 구현과 검증

기존 WorkRecord를 FK로 참조하는 반복 규칙·회차 이력 Branch. 원본 내용·소유자·workspace를 복제하거나 변경하지 않는다. 홈에서는 규칙이 연결된 원본 대신 계산 회차를 기존 행 렌더러에 넣는다. 기존 직접입력/수정 UI, 캘린더, Android 알림 SDK를 재사용한다.

순수 날짜 계산 → 월별/과거 이력 투영 → Home/Calendar 어댑터. 실제 처리만 DB에 저장한다. 매일/지정 요일/격주/매월/매년/실제 완료 후 N일·주, 월말/윤년 복귀를 지원한다. 단일 이동은 논리 키 유지, 앞으로 수정은 규칙 버전 추가. 중지 기간은 소급 표시하지 않으며 종료해도 지난 이력은 남는다.

원격 DB는 work_records 열/권한만 읽었다. 새 migration은 원격 미적용, 격리 PGlite만 실행했다. RPC는 invoker+소유자 RLS, 원본 행 잠금, 예상 버전 검사, UUID 요청 영수증으로 완료/Undo/수정/중복 요청을 직렬화한다. 영수증에 전체 이력을 매번 복사하지 않고 버전만 기록한다. 입력 유실/확인 불가를 성공으로 표시하지 않는다.

## 실행한 검사

- Node 전체 1187/1187 PASS, TypeScript PASS, Android Metro export PASS. Android 설치/실행 PASS가 아님.
- 실제 SQL: 소유자/다른 사용자/anon, 유효 회차, 같은 요청 10회, 버전 충돌, 완료/Undo/건너뜀, 종료 후 이력 유지.
- 실제 저장 함수: 응답 유실 뒤 영수증 확인, JSON 키 순서 차이, 확인 불가, 계정 전환 차단.
- 실제 Android 알림 어댑터+가짜 OS 드라이버: 중복 없음, 종료 시 취소, logout과 예약 경합, 다른 기능 알림 보존. 시간 없는 회차는 예약하지 않음. 전달 검증은 아님.
- 기존 직접입력의 제목/날짜/시간 저장, 실패와 인증 갱신, 입력 보존 등 회귀 통과. 기존 녹음·캡처·Calendar 계약도 전체 회귀에 포함.

## #490 수용 기준 상태

AC-01~11의 날짜/이력·저장 기반과 홈/달력 연결은 구현했으나 일부 조합의 직접 UI/SQL 검증이 아직 부족하다. AC-12는 가짜 OS 경계 검사만 PASS. AC-14 자동 Google 전송/웹 Push 없음. AC-15~18은 격리 DB와 저장 함수 검사 PASS, 실제 동시 기기·운영 권한 검수는 미실행. AC-19는 자동 회귀만 PASS. **AC-13 ERP 실제 화면 검수, AC-20 설치본/실기기 E2E는 미완료**다. 20개 전체 PASS 또는 출시 완료로 표시하지 않는다.

## 남은 제한

- ERP용 get_my_repeating_work_month 읽기 전용 RPC와 readRepeatingMonth 계약, 기존 worklog/worklog-qa scheme의 repeating-work?id=…&date=… 이동 경로를 준비했다. 실제 ERP 화면은 이 저장소 밖이며 기존 부모 행 중복 제거와 표시 연결/기기 이동 검수가 필요하다. 원격 RPC는 아직 적용하지 않았다.
- 연결된 단발 일정은 계산 회차에 중복 표시하지 않고 기존 알림 서비스로 단발 알림을 정리한다. 이 전환의 실제 OS 검수와 과거 반복 미완료의 장기간 계산 성능, 전체 수정·중지/재개·간격형 Undo의 실제 기기 조합 검수가 필요하다.
- 별도 종일/시각 종료시간 입력 확장은 하지 않았다. 회차 시작 시각만 알림에 사용한다.
- 미래 전체 수정의 적용일은 마지막 규칙 적용일보다 뒤여야 한다. 이미 처리한 다음 회차가 있으면 간격형 이전 완료 Undo를 차단한다.
- 사용자 원본/운영 데이터로 테스트하지 않았다. 신규 migration·APK·Production/Play 배포 없음. QA 원격 적용과 기기 검수 전 운영 사용 준비 완료가 아니다.


추가 격리 DB 검사: 원본 WorkRecord 접근 권한이 회수되면 규칙·요청 영수증·ERP 월 조회 모두 0건. 읽기 RPC 호출 후 저장 행 수 불변. 계정 삭제 시 새 개인 테이블의 cascade가 기존 계정 삭제 흐름을 막지 않고 canonical WorkRecord는 기존 SET NULL 계약으로 보존된다. 종료와 계정 삭제는 다른 동작이다. ON DELETE는 명시적 계정 삭제 경계이며 운영 데이터에는 실행하지 않았다.
