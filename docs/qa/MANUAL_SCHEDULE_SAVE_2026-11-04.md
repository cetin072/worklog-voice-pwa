- 공개 운영 서버의 현재 게시 배포 `6ae6bf5d644a48a9f449c0bc`의 소스는 `4000129f6f83dee946edd1f255ba9ae6af1f8577`이다 (Netlify 읽기 전용 조회).
- 그 소스의 `classifiedRecord()`는 `body.dueDate`를 읽지만 실제 일정 분석에는 본문만 사용한다. 선택한 날짜·시간을 별도 필드로 보내는 앱에서는 날짜가 빠지고 짧은 제목이 메모로 분류될 수 있다.
- main에는 #480의 `worklogSchedule()` 수정이 이미 있으므로 새 날짜 파서나 migration을 추가하지 않았다.
- 첨부 화면만으로 설치된 앱의 SHA/API 주소를 확정할 수는 없다. 운영 배포와 main의 차이는 확인했으며, 사용자의 실제 요청 본문·운영 DB를 조회하거나 수정하지 않았다.

## 이번 보완

`persistDraft()`는 선택한 날짜와 응답의 실제 저장 날짜를 비교한다. 시간까지 선택했다면 일정 생성 여부와 일정 ID도 확인한다. 미확인·불일치 응답은 성공 안내 대신 경고를 표시하고 선택한 날짜·시간을 저장 결과에 보존한다. 이미 저장된 업무를 재등록하지 않도록 기존 항목의 연필 버튼으로 수정을 안내한다. 네트워크 오류는 기존대로 입력을 보존한다.

## 실행 검수

- 실제 UI 저장 함수 → 실제 모바일 API 직렬화 → 실제 Netlify handler → 실제 Data Core adapter → 가짜 RPC 경계까지 합성 회의명/짧은 담당자명으로 실행했다. 선택한 금요일 14:30이 due_at 및 일정 starts_at에 유지되고, schedule 분류 및 일정 ID가 UI 결과에 도달했다. 각 저장의 RPC 쓰기 호출은 1회였다.
- 구버전 서버처럼 날짜가 없는 응답, 다른 날짜 응답, 일정 ID 없는 응답을 실행해 경고·선택값 보존·자동 재등록 없음 확인.
- 날짜만 선택한 기한, 동일 시각의 UTC 응답, 날짜 없는 메모 정상 처리 확인.
- 실제 DB/기기 알림/설치본/원격 QA 서버 저장 검사는 하지 않았다. 실제 사용자 데이터나 첨부 화면은 테스트 및 저장소에 사용하지 않았다.
- APK/AAB 생성, Production 배포, DB 변경, Play 제출은 하지 않는다. 요청 시 QA 앱에 누적해서 검수하며, 그때 해당 앱의 API 서버 소스도 함께 확인해야 한다. main 병합은 설치본 또는 운영 서버 배포를 뜻하지 않는다.
