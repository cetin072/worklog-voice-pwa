## A. 결론 먼저 — 제품가치 관점의 1차 위험

1. **입력 경로가 여러 개:** Quick Voice / 직접 입력 / 카카오 캡처 공유 / 갤러리 OCR / 오래된 PWA 음성입력 모두 동일 '기록' 목적을 수행한다. 성공률/완료시간이 낮은 경로를 사용자가 반복 확인하면 선택지 자체가 업무가 될 수 있다.
2. **하나의 일정이 여러 단계:** 입력 → 업무/메모/일정 판단 → 날짜·시간 저장 → 알림 예약 → 필요하면 Google 캘린더 수동 추가/확인 → 홈·캘린더 재조회. '저장 완료'가 실제 원하는 **일정 확정**을 의미하는지 반드시 따로 검사한다.
3. **홈 브리핑의 유용성은 의사결정에 달려 있음:** 카드/배지/일정/업무 수를 보여주는 것 자체는 생산성이 아니다. 사용자가 다음 행동 하나를 빠르게 결정하고 실행했는지 실측해야 한다. 화면 상단 과밀도 경험 제보가 있었다.
4. **회의 녹음은 기능적으로 확인됐지만, 회의록 수기 작성은 기존 노션 AI보다 일이 많을 수 있다.** PR #493 전사 QA 및 AI 요약 실측 전 효과 미확인이다.
5. **사용자가 과거에 이미 보고한 장애 재발 검수 필요:** 직접입력에 날짜/시간이 있어도 메모로 저장; 카카오 캡처 '저장됨' 이후 업무/일정에서 찾을 수 없음; 녹음 완료 후 목록 공백(수정·일부 HUMAN 확인). 과거 수정 커밋/회귀시험만으로 사용자 문제 해결을 전부 확정하지 않는다.
6. **Android 앱과 웹 PWA가 같은 목적의 화면·자동 브리핑을 가진다.** 사용하지 않는 웹 경로의 유지/중복 알림 비용을 평가한다. 다만 인증·기존 Notion 보존·운영 사용자가 남아 있다면 안전하게 유지해야 한다.
7. **개발 기능으로 보이지만 사용자의 직접 시간절약 대상이 아닌 것:** 로그인, 패치노트, 앱 업데이트, 계정·권한, 안전한 재시도, 개인정보 및 보안 기능. 기능 유지를 '시간 절약'으로 점수화하면 잘못된 결론이 된다.

## A-2. 2026-11-08 실기기 스크린샷 증거 — T02 검수 상태

사용자가 QA Android 앱에서 아래 입력을 수행했고 두 장의 결과 화면을 제공했다.

- 제목 **검수용 일정 - 서류 확인**, 2026-11-12 오후 3:00. 홈에 **'업무 저장 완료'**와 **'일정 생성 완료 · 11.12 오후 3:00'** 표시.
- '다가오는 업무' 카드에 **'검수용 일정 - 서류 확인'**, 2026-11-12 날짜 표시. 이 목록은 **WorkRecord 업무 목록이며 일정 Schedule 상세 목록과 동일하지 않다.** 별도 '다가오는 일정'은 화면에서 펼치지 않아 독립 일정 행·ID 검증은 아직 미완료.
- 상단에 **'기록 저장 · 일정 생성 · 기기 알림 예약 미확인'**, 수동 '이 기록의 알림 추가·확인' 버튼. 해당 업무 옆에는 '알림 없음' 표기. **알림 예약 성공/OS 실제 전달은 확인되지 않았다.** 해당 캡처만으로 권한 설정, 알림 서버/Android 실패 중 원인을 확정할 수 없다.
- 2026-11-08 화면에 '오늘 일정 0건'은 11/12 일정과 무관하므로 정상 가능성이 높다.
- 목록에서 **업무별 '수정'(✏️)/'삭제'/큰 '완료'**, 개별 알림 배지, 고정 하단 음성 녹음 및 보조 버튼이 넓은 공간을 차지한다. 직접입력 성공/알림 상태가 **두 개의 큰 성공·경고 카드**에 반복 표기된다.

### 모든 기능 공통 3축 품질 게이트 (사용자 확정)

1. **1순위 CODE / STRUCTURE:** 1개의 사용자 행동이 어떤 소스 데이터/저장/API/알림 연쇄를 일으키는지 그림으로 추적; 책임·입출력·중복 코드·데이터 소유권·실패/재시도/권한/원본 보존/복구 경계를 진단. 확실한 P0/P1 결함은 최소 수정+자동 회귀로 먼저 해결. 문제 없으면 불필요한 리팩터링 금지.
2. **2순위 UI / USABILITY:** 사용자가 실제로 해야 하는 동작 수, 상태 안내 중복·가독성, 삭제 위험, 터치 정확성, 버튼 위계·크기, 320/390px 화면과 키보드/고정 독 가림, 완료 후 다시 찾는 번거로움을 검토. API 성공 메시지가 *실제 의도한 결과*와 일치하는지 확인.
3. **3순위 PRODUCTIVITY / MEASUREMENT:** 기존 메모/Google Calendar/Notion 사용과 같은 과제를 수행해 최종 결과 확인·정정까지 걸리는 실시간/클릭/이동/실패 복구를 비교. **아직 실제 효율 시간 숫자는 없다.**

### T02 코드 책임/실패 경계 현황
```
직접입력(Text/Date/Time)
  ↓ persistDraft (mobile/app/index.tsx)
  ↓ saveWorklog → /api/worklog (서버 확정)
  ├─ WorkRecord 저장
  └─ 조건 충족 시 Schedule 생성 (응답의 scheduleId/scheduleCreated 검증)
       ↓ synchronizeSavedScheduleReminders
       ├─ Android 알림 예약 성공 → 별도 확인
       └─ 미확인/권한 부족 → 원본 WorkRecord·Schedule 성공을 실패로 속이지 않고 경고
  ↓ 홈 직접입력 저장 결과 + '다가오는 업무' (+ 브리핑 일정 목록은 별도 확인)
```

**확인된 UI 중복 수정:** 동일 기록의 저장 결과·알림 안내를 한 결과 영역으로 묶는 [PR #495](https://github.com/cetin072/worklog-voice-pwa/pull/495)를 병합했다(`500e8034`). 업무·일정 및 알림 실제 예약을 별도 결과로 보존하고 알림 확인 버튼은 유지한다. 앱의 실제 화면 반영은 **다음 요청된 QA APK 업데이트 전까지 미적용**이다. 원본 API/저장/알림 로직은 변경하지 않았다. 모바일 CI 472/472 PASS. 노출 버튼과 항목 수를 줄이는 변경은 실제 QA/접근성 테스트 후 별도 검토.

**미확인 사항:** 알림 미예약의 실제 원인(OS 권한·정확 알림 권한·리마인더 상태·동기화 오류), 별도 Schedule 목록 행, 사용자가 느낀 입력 편의성/전체 소요시간. 알림 권한·서버/DB 운영 설정을 자동 변경하지 않는다.

### T02: 저장된 일정의 알림 연결 경계 보완 (PR #496)

- **근거:** save API가 `scheduleId`만 반환하는 레거시 호환성 경로에서는 기존 Android post-save 알림 coordinator로 넘길 Schedule snapshot이 없어 예약을 건너뛰는 코드 경계.
- **변경:** [PR #496](https://github.com/cetin072/worklog-voice-pwa/pull/496) 병합. ID만 받은 경우 기존 `readOwnedReminderSnapshots`로 로그인 사용자 소유의 canonical Schedule을 검증하고 유효한 시각/상태만 기존 알림 coordinator에 전달한다. 정상 완전 응답은 추가 조회 없이 기존 fast path 유지.
- **안전:** 다른 계정·조회 실패·오래된 요청에서 알림/DB를 임의 조작하지 않음. 테스트 **478/478 PASS**.
- **유보:** 사용자 스크린샷의 실제 알림 미예약 원인이 RPC 호환성인지 Android 권한인지 아직 실기기 확정 불가. *코드상 가능한 결함 경로 수정*과 *실제 현장 완전 해결*을 구분.
- **생산성:** 불필요한 알림 재확인 노동을 줄일 가능성이 있으나, 시간 절약 수치는 미측정. 기존 설치 QA 바이너리에는 미반영.

### T03: 캡처 저장 후 취소·알림 정리 경계 보완 (PR #497)

- **근거:** `capture-runtime.ts`의 기존 `undoCapture`는 서버 soft cancel 성공 후 Android 알림 정리까지 성공해야 `undone:true`를 기기 인박스에 저장. 알림 정리 오류가 있으면 **서버는 취소됨, UI는 취소 실패**로 분리될 수 있었다.
- **변경:** [PR #497](https://github.com/cetin072/worklog-voice-pwa/pull/497) 병합. 서버 취소 확정 즉시 인박스에 `undone:true` 체크포인트 저장, 이후 기기 알림 정리는 별도 시도. 실패 시 취소 성공은 유지하고 **'알림 정리 확인 필요'** 경고 표시. 취소 후 경고 UI 보존; 화면 이름을 '캡처로 업무·일정 등록'으로 변경.
- **검증:** 테스트 **480/480 PASS**. 합성 서버 취소 성공→Native cleanup 실패→재오픈에도 취소 상태·중복 저장 없음. 캡처 실제 실기기 공유/분석 정확도는 미검증.
- **생산성:** 이미 취소한 업무를 재차 취소하고 확인하는 부담 방지 가능; 실측 미완료. 기존 QA 앱에는 미반영.

### T01: 빠른 음성 vs 직접 입력 — 재시도 안전성 검수 (2026-11-08)

**판정: 직접 입력 FIX / 음성 입력은 유지·효율 VERIFY. CODE·합성 런타임 검증이며 HUMAN·MEASURED는 아직 없음.**

| 항목 | 빠른 음성 | 직접 입력 |
|---|---|---|
| 정상 동선 | 시작 → 말하기 → 종료 → 자동 저장·브리핑 조회 | 입력 열기 → 타이핑 → 필요 시 날짜·시간 선택 → 저장·브리핑 조회 |
| 인식/오타 정정 | 저장 후 브리핑에서 해당 기록 수정; 전사 품질에 따라 추가 노동 | 저장 전 원문 수정 가능; 날짜·시간은 별도 선택 |
| 저장 응답 유실 | 기존 immutable attempt가 같은 요청 ID·원문·시각 유지 | **기존에는 저장 버튼을 다시 누를 때 새 ID를 만들어 중복 기록 가능. 이번 수정에서 같은 입력의 ID·원문·기록 시각·선택 날짜/시간 유지** |
| 연속 저장 누르기 | 기존 in-flight + attempt promise 재사용 | 동기 latch + 동일 attempt promise로 중복 요청 차단 |
| 저장 후 안내 실패 | 저장/브리핑 결과를 별도 취급하는 flow 존재 | **정확 알림 권한 안내의 기기 저장/조회 실패를 기록 저장 성공과 분리** |
| 복구 범위 | 계정별 전사문 기기 임시 저장·복구 | 이번 변경은 동일 계정 Home 인스턴스의 메모리 재시도만 보호. 앱 종료/재실행 후 복구는 미구현 |
| 효율 | 실제 기기 인식·오타·수정·조회 시간을 포함해야 판정 가능 | 실제 키보드 입력·날짜 선택·저장·조회 시간을 포함해야 판정 가능 |

- `manual-work-save.ts`는 검증된 Quick Voice의 immutable attempt 구조를 대상 영역에 작게 복제했다. STT 모듈에 의존하지 않고 기존 `saveWorklog` API 계약을 그대로 사용한다. 입력 내용/날짜/시간을 바꾸면 새 의도로 취급하고, 완료 후 입력 초기화 시 attempt도 해제한다. **내용 변경·앱 종료 이후까지 포괄하는 중복 방지 보장은 아니다.**
- Home이 user ID로 재마운트되는 기존 경계를 유지한다. 토큰 갱신 후에도 같은 입력의 재시도 키는 유지하며, 저장 함수는 현재 로그인 토큰을 사용한다. DB/RPC/권한/native/provider 계약 변경은 없다.
- 실제 `persistDraft` 함수를 실행하는 합성 UI 런타임에서 응답 유실→수동 재시도 동일 payload, 빠른 이중 누르기 1회 전송, 저장 후 권한 안내 예외→성공 유지·입력 초기화를 확인한다. 기존 UI→HTTP→handler→RPC 일정 생성 검사도 유지한다.
- UI는 변경하지 않았다. 음성 오류 수정은 저장 후 카드 찾기·편집을 요구하고, 직접 입력은 날짜·시간 선택 단계가 더해진다. 어느 쪽이 더 빠른지는 문장 길이·인식 정확도·작업 종류에 따라 달라지므로 현재 우열을 확정하지 않는다. 홈 큰 버튼/도크 재배치는 계속 보류한다.
- 후속 검증 포인트: Home `refreshBriefing`이 오류를 화면 상태로 처리하고 resolve하므로 음성 flow의 별도 `refresh_error` 안내와 실제 목록 상태가 일치하는지 추가 재현 필요. 이번 수정 범위에 포함하지 않았다.
- 실기기 비교 과제: 동일한 짧은 업무와 날짜·시간이 있는 일정 각각을 음성/직접 입력으로 수행해 **정확한 최종 목록 조회·정정까지** 측정한다. 현재 시간 수치·절감률은 없다. QA APK/Play/운영 배포는 수행하지 않는다.

### 보류한 큰 UI 개편안 (사용자 사전 승인 필수)

## D. 효과 측정 기록 형식과 계산

표의 각 행을 최소 단위로 기록한다. 기술 관점(실행 성공)과 제품 관점(시간 절약)은 별도 판단.

`기능 ID | 시험 ID | 사용 빈도/주 | 기존 방식 완료시간(초) | 업무수첩 완료시간(초) | 복구·수정 추가시간(초) | 정확성/실패 | 사용자 평가 | 판정 | 근거`

- **기존 방법**과 **업무수첩 방법** 모두 최종 결과가 원하는 위치에 실제 저장·표시되는 시점까지 포함.
- 업무수첩 순시간 = 녹음/입력 + 모델 다운로드/전사 대기 + 수정 + 재시도 + 저장 확인 + 다른 앱 조회 + 검색/동기화 비용.
- `1회 절약 = 기존 방식 완료시간 − 업무수첩 전체 완료시간`.
- `주간 순절약 추정 = 측정된 1회 절약 × 실제 주간 실행 횟수 − 유지/오류복구에 든 시간`. 실측 없으면 공란.
- **핵심 품질 지표:** 정확한 결과 저장률, 후속 수정률, 재시도·중복 등록률, 결과 재검색까지 걸린 시간, 불필요한 알림, 회의록 교정시간.
- 예시 잠정 유지 기준: 기존 방법과 품질이 같거나 더 좋고, 사용자의 유의미한 반복 업무에서 **20% 이상 시간 절약** 또는 실제 누락 방지 등 명확한 가치. 수치는 **검증 기준 가설**, 현재 달성률이나 절감 측정값이 아니다.
- 반복 사용의 이유를 따로 묻는다: 정말 편해서인지, 이미 설치되어 있기 때문인지, 대안이 없어서인지.

| SIMPLIFY | 목적은 유용하지만 단계·탭·설정이 불필요하게 많음 | 제거할 조작 단계부터 검토, 새 기능 추가 금지 |
| MERGE | 서로 다른 메뉴·앱이 동일 결과를 중복 생성 | 단일 경로를 정하되 이전 기록·권한·동기화 보존 |
| PAUSE | 아직 미사용/체감 가치를 판단할 근거 부족 | 신규 개발 보류, 기존 원본 손대지 않음 |
| REMOVE_CANDIDATE | 장기간 미사용 + 명확한 중복/음수 효율 | 삭제 전 실제 사용자·데이터·의존성 확인 및 별도 승인 |

## F. 사용자 실사용 검수 질문 — 한 기능씩 최소 질문

각 시험이 끝날 때 사용자에게 **한 가지만** 확인한다.

1. 이 기능을 실제로 일주일에 몇 번 쓰는가?
2. 같은 업무를 다른 앱/예전 방식으로 하면 무엇이 더 빠른가?
3. 저장 후 결과를 다시 확인하거나 수정해야 하는가?
4. 현재 기능이 사라져도 불편하지 않겠는가?

최종 판정은 자동검사 결과, 사용자의 설명, 실측값을 종합하되 **코드 가동 = 제품가치 확보라고 기록하지 않는다.**
