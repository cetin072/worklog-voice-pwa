## Findings and implementation

This is a measured improvement to the current path, **not proof of a recent regression**. The account gate already existed in the November 10 QA version. Historical #537 first-touch timings came from different CI runs and are not a baseline here.

- `mobile/src/providers/platform-provider.tsx`: configuration and initial URL lookup run together. Session and server getUser checks have the existing 15-second request deadline. The SDK does not accept the wrapper's AbortSignal, so this bounds waiting/publication, not necessarily the underlying transport. An expired attempt cannot later publish. The auth listener is installed before awaiting verification, so logout/account replacement during boot supersedes the initial session.
- `mobile/src/platform/local-account-gate.ts`: cleanup/preparation and server identity verification overlap; both settle before publication. A stale epoch cannot confirm ownership or publish. Verification failure clears even same-account retained alarms before reporting failure. Cleanup failure never grants access. Auth callbacks still defer work outside the Supabase listener lock.
- `mobile/src/features/schedule/schedule-reminder-service.ts`: an optional `accountScope` in the existing encrypted v3 state contains project URL, data schema and user ID. Only successful server verification followed by guarded confirmation establishes it. Same-scope restart also checks the OS snapshot against stored reservation contents. Missing proof, account/project change, interrupted intents, unknown/mismatched alarms still take cleanup. Corrupt state fails closed. The marker is removed in the durable cancellation journal before OS mutation; cancellation failures/crashes retain all IDs for retry. Cleanup uses one initial and one final OS snapshot, instead of repeating storage/list operations for every schedule and all six offsets. It never calls global cancel-all or touches unrelated notifications/server data. Existing offset/title/time values are unchanged on a proved same-account restart.
- The first startup after upgrading an older state has **no owner proof and still cleans up**. The follow-up now journals a private, scope-bound legacy offset queue before cancellation. It restores only after server identity and exact canonical schedule ownership verification; see the follow-up section below. Future proved same-account restarts still preserve existing reservations. Explicit logout/login and invalid identity clear OS reservations.
- `mobile/app/index.tsx`: background reminder recovery and initial briefing now follow client/account lifetime, avoiding duplicate recovery and reads on a same-owner token rotation. Auth events still invalidate work on actual owner changes/logout. `setBriefing(next)` remains **before** awaiting reminder recovery; recovery was not the full first-render gate. Foreground/manual refresh and offline calendar retry remain intact.
- `mobile/src/features/recurring/use-repeating-work.ts`: an unchanged read retains the prior snapshot identity, avoiding an unnecessary native reminder synchronization. Newer locally confirmed versions still win over slow reads.
- `mobile/src/features/startup/startup-timing.ts`: opt-in `EXPO_PUBLIC_STARTUP_TIMING=1` logs fixed stages and duration/outcome only. Config, session, identity, notification preparation, account gate, briefing, recovery, recurring read, month calendar and Google read are instrumented. No account/project IDs, URL, token, work text, payload or error text enters this diagnostic. These are stage execution timings, not screen paint/touch measurements; recovery has its existing internal error handling. No analytics service or persisted telemetry was added.
- Month-calendar and Google queries still serve the currently visible date range and keep their current owner/range stale-response guards. No speculative cross-account cache or stale result is used to declare startup ready. Broader query/window reduction is deferred because the current UI requires these records; new timings allow a device run to identify whether these stages warrant more work. No whole-app UI rewrite.

## Follow-up: verified legacy custom-offset recovery

The initial PR safely cancelled unknown-owner reservations but could lose their custom offsets. The follow-up preserves a **private migration candidate**, not an assertion that old data belongs to the current account:

1. `schedule-reminder-service.ts` journals only valid Schedule UUIDs and supported minute offsets in encrypted v3 state, together with the exact first attempted project URL/schema/account scope. It does not copy old title, timestamp, content or native identifiers into this queue. Unknown-owner live OS reservations are still cancelled and absence confirmed before account publication. A known different account's state is never recategorized as legacy data.
2. `legacy-offset-recovery.ts` runs in the existing background Home recovery before ordinary canonical reconciliation. `readOwnedReminderSnapshots` checks server identity before/after the complete batched query, uses existing RLS plus an explicit `created_by_user_id` filter, validates every row/count, and rejects owner changes or stale epochs. The returned owner must equal the candidate scope's account. The whole read has a 15-second deadline. No missing-row inference authorizes a reservation.
3. Only owned, confirmed, timed schedules receive the preserved offsets; the **current server title and start** supply the reservation, and an already-past offset is discarded. Deleted, inaccessible, different-owner, cancelled, completed and all-day schedules are not restored. After a successful complete query, unmatched candidates are discarded instead of carried into another login. The queue is never shown in UI or logged.
4. Each offset is removed only after the durable reservation settles. A crash/lost native acknowledgement retries idempotently. If a restart requires cleanup of a partially restored batch, already-restored proved offsets are re-collected before cancellation so they are not lost. Explicit single-offset and whole-schedule cancellation remove their migration candidates; late lookup results cannot recreate them. Existing cancellation intents and ambiguous cleanup-only records are not treated as affirmative user settings.
5. A failed initial identity check still clears OS reservations and blocks publication, but its private queue stays bound for a later successful verification of that exact account/project. A canonical read/network/permission failure similarly retains the queue without scheduling, permission prompts or claiming success. Explicit logout/login cleanup or a different account/project discards it.

Limits are deliberate: we cannot recover offsets already erased by an older app or the initial PR version. If no session account can be restored on the first migration, cleanup has no safe account scope and cannot retain a candidate for a guessed future login. Orphan OS-only reservations, malformed/unsupported records, cancellation-only evidence, and unconfirmed interrupted replacement settings do not provide safe restoration evidence. Legacy state cannot prove its historical project; a candidate is scoped at migration and only exact UUIDs owned by the verified current account may restore. A wrong account used for the first migration can cause unmatched offsets to be discarded, and they are not later transferred to the correct account. Future triggers that pass while offline are not fired immediately. An older app downgrade may drop the new private queue. There is no atomic transaction spanning a remote server edit and native scheduling; local stale guards and subsequent canonical recovery remain the convergence mechanism. No unconditional preservation guarantee is made.
