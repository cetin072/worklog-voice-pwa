# 사용자 프리뷰 요청 전 QA Gate

이 문서는 사용자를 디버거로 쓰지 않기 위한 필수 검수 기준이다.

## 목적

사용자에게 "한번 눌러보세요", "캡처해서 보내주세요", "휴대폰에서 확인해주세요"라고 요청하기 전에 개발자가 기계적으로 확인 가능한 오류를 먼저 제거한다.

사용자 실기 검수는 **실제 기기에서만 판단 가능한 항목**에 한정한다.

---

## 절대 규칙

다음 항목이 하나라도 미확인/실패이면 사용자에게 프리뷰 검수를 요청하지 않는다.

1. 최신 `main` 대비 behind 여부와 충돌 여부 확인
2. 변경 파일 전체 diff 검수
3. 기존 핵심 기능 회귀 여부 확인
4. 자동 테스트 통과
5. 새 기능의 전용 테스트 존재 및 통과
6. 빌드 산출물/런타임 의존 파일 존재 확인
7. Deploy Preview 빌드 `Ready` 확인
8. Preview URL에서 핵심 정적 자산 및 API/Worker/WASM/모델 경로가 실제 접근 가능한지 확인
9. 브라우저에서 자동화 가능한 사용자 흐름은 E2E 또는 동등한 자동 검증 수행
10. 실패 시 사용자의 입력/첨부가 유실되지 않는지 확인

`Netlify Ready`, `npm test 통과`, `코드상 문제없어 보임` 중 하나만으로 사용자 검수를 요청해서는 안 된다.

---

## 사용자에게 넘기기 전에 확인할 흐름

기능에 맞는 대표 정상 경로를 처음부터 끝까지 확인한다.

예시 — 문서 스캔/OCR:

`문서 스캔 → 촬영/파일 선택 → 사진 표시 → 모서리 조정 → 보정 결과 → 스캔 사용 → OCR 실행 → OCR 결과 표시 → 업무 내용 반영 → 저장 요청`

이 흐름에서 코드/자산/브라우저 자동화로 검증 가능한 단계는 모두 개발자 쪽에서 먼저 검증한다.

OCR처럼 런타임 자산이 필요한 기능은 테스트 이미지 fixture를 사용해 **실제 엔진을 최소 1회 실행**하는 검사를 우선한다. 단순히 파일 이름이 존재하는지만 검사하는 것으로 끝내지 않는다.

---

## 사용자에게 요청해도 되는 검수

아래처럼 실제 기기/실제 환경의 체감이 필요한 경우에만 요청한다.

- 삼성/안드로이드에서 실제 카메라가 원하는 방식으로 열리는가
- 손가락 드래그 조작감이 자연스러운가
- 실제 업무 문서에서 OCR 정확도가 업무에 쓸 만한가
- 화면 크기, 가독성, 버튼 위치가 사용하기 편한가
- 실제 업무 흐름에서 빠진 요구사항이 있는가

반대로 다음은 사용자에게 발견시키면 안 된다.

- JS/WASM/Worker/모델 파일 누락
- 404 경로
- 초기화 예외
- 버튼 이벤트 미연결
- 빌드 설정 오류
- 기존 기능 회귀
- API 라우트 누락
- 기본 정상 경로에서 발생하는 명백한 런타임 오류

---

## 프리뷰 요청 보고 형식

사용자에게 테스트를 요청할 때는 먼저 아래를 짧게 보고한다.

- `자동 테스트: PASS`
- `전용 기능 테스트: PASS`
- `Deploy Preview: READY`
- `런타임 자산/경로: PASS`
- `자동화 가능한 대표 흐름: PASS`
- `사용자에게 남은 검수: <실기에서만 확인 가능한 항목>`

위 PASS를 실제로 확인하지 않았다면 적지 않는다.

---

## 반복 버그 발생 시

동일 종류의 오류가 사용자 실기에서 발견되면 단순 패치로 끝내지 않는다.

1. 원인을 수정한다.
2. 그 오류를 재현하는 자동 테스트 또는 검증 단계를 추가한다.
3. 이 QA Gate에서 같은 유형을 사전에 잡을 수 있는지 확인한다.
4. 이후에만 다시 사용자 검수를 요청한다.

즉, **사용자가 발견한 버그는 다음부터 사용자가 다시 찾지 않도록 자동 검수 자산으로 남긴다.**
