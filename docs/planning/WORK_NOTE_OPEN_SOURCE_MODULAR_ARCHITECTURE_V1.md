# 업무수첩 오픈소스 우선·모듈형 개발 원칙 V1

## 0. 문서의 역할과 상위 원칙

이 문서는 업무수첩의 신규 기능, 외부 연동, AI 기능, 입력 파이프라인을 설계할 때 사용하는 장기 개발 기준이다.

이 문서는 보안·권한·데이터 무결성·사용자 승인 경계를 약화시키지 않는다. 또한 특정 기술이나 오픈소스를 영구 고정하는 목록이 아니라, **새로 만들기 전에 기존 구현을 찾고, 실제 교체가 필요한 경계에서만 모듈화하며, 총비용과 유지보수성을 함께 최적화하는 판단 원칙**이다.

핵심 우선순위는 다음과 같다.

1. 기존 업무수첩 Platform/Core에 이미 있는 기능
2. OS·Expo·Supabase·Google 등 현재 채택한 플랫폼의 공식 기능/SDK
3. 유지보수되는 검증된 오픈소스·라이브러리
4. Adapter/Service를 통한 연결·확장
5. 필요한 최소 자체 구현
6. 최후의 수단으로 Fork 및 자체 유지보수

즉, **범용 기능을 다시 만드는 것보다 이미 검증된 구현을 재사용하고, 우리 고유 업무 로직에 개발 역량을 집중한다.**

---

## 1. 목적

업무수첩은 모든 기능을 처음부터 직접 개발하는 프로그램이 아니다.

핵심 목표는 다음과 같다.

**업무 플랫폼의 공통 뼈대를 만들고, 범용 기능은 검증된 공식 기능·오픈소스·외부 모듈을 조립하며, 실제 교체 가능성이 있는 기능은 모듈형 경계로 개발한다.**

직접 개발 역량은 범용 기술을 다시 만드는 데 사용하지 않고 다음과 같은 업무수첩 고유 영역에 집중한다.

- 사용자의 기록을 실제 업무로 판단
- 일정과 할 일 구분
- 담당자·기관·고객 연결
- 완료 / 진행 / 할 일 / 후속조치 / 확인사항 구분
- 업무 간 연관관계 관리
- 중요 업무 및 보고 필요성 판단
- 회사별·기관별 업무 분리
- 기록에서 실제 행동으로 연결

---

## 2. 최상위 개발 원칙

새 기능을 직접 만들기 전에 반드시 다음 순서로 검토한다.

**기존 Platform/Core 확인**
**→ 공식 SDK/API 확인**
**→ 검증된 오픈소스·기존 라이브러리 조사**
**→ Adapter/Service로 연결**
**→ 설정·확장·Plugin 사용**
**→ 필요한 최소 수정**
**→ 최후의 수단으로 Fork 및 자체 유지보수**

기본 원칙:

> 이미 잘 만들어진 범용 기능은 다시 만들지 않는다.

단, 오픈소스라는 이유만으로 무조건 채택하지 않는다. 유지보수 상태, 라이선스, 보안, 성능, 배터리/리소스 사용, 운영비, 통합 난이도, 장애 대응 비용까지 포함한 **총비용**으로 판단한다.

## 3. 모듈 교체형 구조

업무수첩의 주요 외부 엔진과 서비스 경계는 특정 회사나 특정 공급자에 과도하게 종속시키지 않는다.

예시:

```text
업무수첩 Core
    │
    ├── Calendar Adapter
    │       ├── Native Calendar / OS Calendar Provider
    │       ├── Web Calendar UI
    │       └── 외부 Calendar API
    │
    ├── STT Adapter
    │       ├── Local STT
    │       ├── Server STT
    │       └── Cloud STT API
    │
    ├── OCR Adapter
    │       ├── Local / Native OCR
    │       ├── Server OCR
    │       └── Cloud OCR
    │
    ├── Document Parser Adapter
    │       ├── 범용 Parser
    │       └── 파일형식별 보완 Parser
    │
    ├── AI Adapter
    │       ├── Local LLM
    │       ├── OpenAI 등 외부 AI
    │       └── 기타 모델
    │
    └── Notification Adapter
            ├── Native Local Notification
            ├── FCM / Web Push
            ├── 이메일
            └── 기타 알림 채널
```

중요: 모든 내부 코드를 억지로 Adapter화하지 않는다. **실제 교체 가능성이 있거나 외부 공급자/런타임과 연결되는 경계에서만 Adapter를 둔다.** 업무수첩의 핵심 데이터 모델과 업무 규칙은 불필요한 추상화로 감싸지 않는다.

## 4. 오픈소스 사용 원칙

오픈소스는 단순한 무료 코드 복사본으로 취급하지 않는다.

오픈소스를 사용하는 이유는 다음과 같다.

- 이미 구현된 기능 활용
- 다수 사용자가 발견한 버그 수정 결과 활용
- 성능 최적화 결과 활용
- 예외 처리 및 호환성 확보
- 개발시간 절감
- 개발비 절감
- 자체 개발에 따른 신규 버그 감소

다만 오픈소스도 버그가 없다는 의미는 아니다.

**직접 처음부터 개발할 때 발생할 수 있는 많은 문제를 이미 다른 개발자들이 발견하고 개선해 왔다는 장점을 활용한다.**

## 5. 오픈소스 수정 원칙

가능하면 오픈소스 원본 코드를 직접 크게 수정하지 않는다.

우선 다음 구조를 사용한다.

```text
업무수첩
    ↓
우리 Service / Adapter
    ↓
오픈소스 / 공식 SDK
```

필요 기능이 없을 경우:

1. 설정으로 해결 가능한지 확인
2. Adapter에서 확장 가능한지 확인
3. Plugin 또는 Extension 방식 확인
4. 작은 수정으로 가능한지 확인
5. 위 방법이 불가능한 경우에만 Fork

Fork 후 자체 버전을 운영하는 것도 가능하나 원본 업데이트·보안 패치·버그 수정과의 병합 비용을 고려한다.

## 7. 현재 우선 검토 기술군

이 목록은 고정 채택 목록이 아니라 **기능 개발 시 우선 조사할 후보군**이다. 도입 시점에 최신 유지보수 상태와 라이선스를 다시 확인한다.

### 일정

웹/PWA 달력 UI는 FullCalendar 계열 등 검증된 웹 캘린더를 우선 검토한다.

모바일 앱은 React Native/Expo 환경에 맞는 Native Calendar / OS Calendar Provider를 우선 검토한다. 웹용 UI 라이브러리를 모바일에 억지로 재사용하지 않는다.

### 음성인식

Whisper 계열, 로컬 STT, 서버 STT, Cloud STT를 Adapter 뒤에서 비교한다.

- 데스크톱/서버 환경: faster-whisper 등
- 모바일 온디바이스: 모바일 런타임에 적합한 Whisper 계열/ONNX 계열 구현 등
- 정확도·속도·운영편의성이 유리하면 외부 STT API도 교체 가능한 선택지로 둔다.

### OCR

PaddleOCR 등 검증된 OCR 엔진을 우선 조사하되, 모바일에서는 native/온디바이스 OCR과 서버 OCR의 배터리·속도·앱 크기·정확도를 함께 비교한다.

### 문서 읽기

Microsoft MarkItDown 등 범용 문서 변환 도구를 우선 조사한다.

PDF, Word, Excel, PowerPoint, HTML, CSV 등 파일 형식마다 별도 분석기를 처음부터 만들기보다 가능한 한 공통 텍스트/구조화 단계로 변환한다.

### 데이터베이스

기본 방향은 PostgreSQL 기반이다.

현재는 Supabase/PostgreSQL을 중심으로 사용하되, **현재 정상 동작하는 Data Core를 추상화 목적만으로 재작성하지 않는다.** 장기 이전 가능성을 위해 스키마·SQL·데이터 소유권을 명확히 유지하고, 외부 공급자 고유 기능 의존은 필요한 범위에서만 사용한다.

### 알림

초기에는 다음을 우선한다.

- Native Local Notification
- Web Push / FCM Push
- 앱 내부 알림

문자·알림톡 등 건당 비용이 발생하는 채널은 필요한 경우에만 사용한다.

## 8. 비용 원칙

업무수첩 초기 단계에서는 다음을 기본 방향으로 한다.

> **기존 인프라 재사용 + 오픈소스 + 자체처리 + 무료구간 우선**

목표는 불필요한 초기 고정비를 최소화하는 것이다.

다만 무료 여부만으로 판단하지 않는다. 다음 비용을 함께 본다.

- 개발시간
- 서버 CPU/GPU
- 저장공간
- 네트워크
- 배터리·모바일 성능
- 백업
- 외부 AI API
- 문자/알림톡
- 유지보수 및 장애 대응
- 상용 Premium 기능

**몇 원의 Cloud API 호출이 복잡한 자체 운영보다 더 싸고 안정적이면 Cloud를 선택할 수 있다.**

## 9. 비용 발생 시점 원칙

사용량이 증가하면서 무료 또는 자체 시스템의 한계가 확인된 경우에만 유료 서비스 도입을 검토한다.

예:

```text
초기
로컬/사내 STT
        ↓
사용량 증가
        ↓
처리속도·운영부담 한계
        ↓
GPU 서버 또는 유료 STT 비교
```

유료 서비스는 다음 중 하나 이상이 명확한 경우 도입한다.

- 처리속도 크게 개선
- 정확도 크게 개선
- 장애 감소
- 유지보수 시간 절감
- 보안 향상
- 개발비 절감 효과가 API 비용보다 큼

## 10. AI 사용 원칙

업무수첩의 모든 작업에 생성형 AI를 사용하지 않는다.

AI가 필요 없는 작업은 일반 프로그램, DB query, 규칙, OS 기능, 검증된 엔진을 사용한다.

예:

```text
이미지
 ↓
OCR
 ↓
텍스트
```

```text
음성
 ↓
STT
 ↓
텍스트
```

여기까지는 생성형 AI API가 필수적이지 않다.

## 11. 일정·할 일 추출 구조

텍스트가 생성되면 먼저 결정론적 처리를 사용한다.

1차 규칙 기반 처리 대상:

- 날짜
- 시간
- 전화번호
- 이메일
- 금액
- 명확한 장소
- 명확한 사람 이름 후보
- 명확한 일정 표현
- 명확한 할 일 표현

예:

```text
9월 22일 오후 2시
창원시청에서
김정원 과장 미팅
```

이런 내용은 AI 없이도 상당 부분 처리할 수 있다.

규칙 파서는 보수적으로 동작하고, 애매한 경우 잘못된 자동확정보다 AI 판단 또는 사용자 확인으로 넘긴다.

## 12. AI가 필요한 영역

다음처럼 의미와 문맥 판단이 필요한 경우 AI를 사용한다.

```text
강 대표 내려오면
지난번 이야기한 자료 가지고
한번 보자.
```

```text
다음 주 중에 범한 쪽 한번 연락해서
추석 전에 가능한지 알아봐.
```

판단 대상:

- 일정인지 할 일인지
- 담당자가 누구인지
- 언제까지 해야 하는지
- 무엇을 준비해야 하는지
- 앞선 기록의 무엇을 가리키는지
- 캘린더 등록이 필요한지
- 단순 참고사항인지 실제 행동사항인지

이런 작업에는 AI를 활용한다.

## 13. AI 비용 최소화 구조

모든 입력을 바로 유료 AI API로 보내지 않는다.

```text
음성 / 이미지 / 문서
        ↓
STT / OCR / Parser
        ↓
      텍스트
        ↓
규칙 기반 분석
        ↓
┌─────────────────┐
│ 명확한 내용인가? │
└───────┬─────────┘
        │
   YES  │  NO
    ↓   │   ↓
자동처리 │ AI 판단
        │   ↓
        └→ 결과 저장
```

---

## 14. 향후 AI 3단계 구조

기본 방향은 다음과 같다.

```text
1. 일반 프로그램 / 규칙
          ↓
2. 합리적인 경우 Local AI
          ↓
3. 필요한 경우 외부 AI API
```

즉 **Deterministic First**가 원칙이다.

Local AI와 Cloud AI 중 무엇을 쓸지는 정확도, 지연시간, 배터리, 장치 성능, 서버 운영비, 개인정보, 사용량을 비교해 결정한다. Local AI를 절대 규칙으로 두지 않는다.

## 15. 공통 입력 처리 파이프라인

입력 종류마다 완전히 별도 시스템을 만들지 않고 가능한 한 공통 파이프라인으로 통합한다.

```text
              [업무수첩 입력]

     음성          이미지          문서
      ↓              ↓              ↓
     STT            OCR           Parser
      └──────────────┼──────────────┘
                     ↓
                  공통 텍스트
                     ↓
                규칙 기반 분석
                     ↓
                  AI 판단
              필요 시에만 사용
                     ↓
       ┌─────────────┼─────────────┐
       ↓             ↓             ↓
      일정           업무          기록
       ↓             ↓             ↓
    Schedule      Data Core      Archive
```

이 구조를 기반으로 다음 입력을 공통 분석 엔진에 연결한다.

- 음성메모
- 통화녹음
- 회의록
- 카카오톡/문자 캡처
- PDF 공문
- Word/Excel/PPT 자료
- 이메일
- 사진 기록

## 16. 업무수첩의 진짜 핵심 기능

범용 기술 자체는 업무수첩의 핵심 자산이 아니다.

OCR, STT, 달력, 데이터베이스, 파일 업로드 등은 가능한 한 검증된 기술을 활용한다.

업무수첩이 직접 개발하고 축적해야 할 핵심은 다음이다.

### 업무 이해

- 실제 업무인지
- 참고사항인지
- 아이디어인지
- 일정인지
- 할 일인지
- 후속조치인지

### 업무 연결

- 담당자
- 기관
- 회사
- 고객
- 프로젝트

## 17. 신규 기능 개발 전 의무 검토

Codex/Work/ChatGPT 또는 사람이 새 기능 개발을 시작하기 전에 다음을 확인한다.

1. 이 기능이 줄이는 실제 사용자 업무는 무엇인가?
2. 기존 업무수첩 Platform/Core에 이미 있는가?
3. OS·Expo·Supabase·Google 등의 공식 SDK/API로 해결 가능한가?
4. 동일 기능의 검증된 오픈소스가 존재하는가?
5. 라이선스가 사용 목적에 적합한가?
6. 최근에도 유지보수되고 있는가?
7. 사용자·커뮤니티·실사용 사례가 충분한가?
8. 알려진 심각한 보안 문제가 없는가?
9. 현재 웹/모바일/서버 런타임에 맞는가?
10. Adapter로 감싸는 것이 실제로 필요한 교체 경계인가?
11. 자체 개발하는 것보다 실제로 시간과 총비용을 줄이는가?
12. 유료 서비스라면 얻는 이익이 비용보다 큰가?
13. AI 없이 규칙/코드/DB/OS 기능으로 해결 가능한가?

위 질문을 검토하지 않고 범용 기능을 처음부터 새로 개발하지 않는다.

## 18. 개발 우선순위

### 1순위 — 업무수첩

업무수첩에서 먼저 검증한다.

- 공통 입력 구조
- 음성 전사
- OCR
- 문서 읽기
- 일정 추출
- 할 일 추출
- AI 최소 사용
- 필요한 경계의 모듈 교체 구조
- 저비용 운영 구조

### 2순위 — 태장 홈페이지·업무플랫폼

업무수첩에서 검증한 원칙을 태장 업무플랫폼 등 다른 제품에도 재사용한다.

특히:

- 모듈화
- Adapter
- Existing First
- 검증된 오픈소스 활용
- 자체 개발 최소화
- 무료구간/기존 인프라 우선
- 공급업체 종속 최소화

을 공통 원칙으로 사용한다.

## 19. 개발 작업 지시 기준

앞으로 Codex/Work가 새로운 기능을 구현할 때 다음을 기본 지시로 적용한다.

> 범용 기능을 직접 구현하기 전에 기존 Platform/Core와 공식 SDK를 먼저 확인하고, 그 다음 검증된 오픈소스와 기존 라이브러리를 조사한다.
>
> 오픈소스를 사용할 경우 라이선스, 최근 유지보수 상태, 보안, 성능, 통합 난이도, 총운영비를 검토한다.
>
> 원본 코드 직접 수정은 최소화하고, 실제 공급자/엔진 교체가 필요한 경계에서는 Adapter 또는 Service 계층을 두어 교체 가능한 구조로 연결한다.
>
> 초기 운영은 기존 인프라, 오픈소스, 자체 처리, 무료구간을 우선하되 무료 자체 운영이 유료 API보다 더 비싸거나 불안정해지는 경우 총비용 기준으로 다시 판단한다.
>
> OCR·STT·문서 파싱·날짜 및 명확한 일정 추출 등 결정론적으로 처리 가능한 작업에는 생성형 AI를 기본 엔진으로 사용하지 않는다.
>
> 문맥과 의미 판단이 필요한 부분에만 AI를 사용하고, 기본 구조는 규칙/코드 → 필요 시 Local AI → 필요 시 외부 AI API 순으로 검토한다.
>
> 특정 서비스에 종속되지 않도록 외부 엔진과 공급자 경계는 교체 가능성을 고려하되, 현재 안정적인 내부 Core를 추상화 목적만으로 재작성하지 않는다.

## 20. 최종 원칙

업무수첩은

**“모든 기능을 직접 만든 거대한 프로그램”**

이 아니라,

**“검증된 기술을 필요한 경계에서 교체 가능한 부품으로 조립하고, 그 위에 우리 업무를 이해하고 행동으로 바꾸는 두뇌를 얹은 업무 플랫폼”**

으로 개발한다.

최종 목표는 다음을 동시에 달성하는 것이다.

- 빠른 개발
- 낮은 초기비용
- 낮은 버그 위험
- 좋은 성능
- 서비스 종속 최소화
- 지속적인 업그레이드 가능
- 필요 시 자체 수정 가능
- 사용량 증가에 따른 단계적 확장
- 핵심 업무 지식과 데이터의 내부 통제
- 사용자가 반복해서 해야 하는 업무를 실제로 하나씩 줄이는 것
