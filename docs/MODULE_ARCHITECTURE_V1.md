# 업무수첩 모듈 아키텍처 V1

## 목적

업무수첩이 기능 추가에 따라 거대한 단일 앱으로 얽히지 않도록, 각 업무도구의 독립성과 연결 방식을 정의한다.

핵심 원칙은 다음 한 문장이다.

> **각 기능은 단독으로 완성하고, 업무수첩은 완성된 기능들을 연결한다.**

## 1. 전체 구조

```text
업무수첩 App Shell
│
├─ 업무기록 모듈
├─ 일정 모듈
├─ 문서 스캔/PDF 모듈
├─ 통화정리 모듈
├─ 회의정리 모듈
├─ 메일 업무화 모듈
├─ 캡처 분석 모듈
├─ CRM 모듈
└─ 브리핑 모듈
       │
       ↓
공통 Adapter / Services
├─ Worklog / Notion Adapter
├─ Schedule Adapter
├─ CRM Adapter
├─ Storage Adapter
├─ STT Adapter
├─ AI Adapter
├─ Kakao Adapter
├─ Auth / Permission
└─ Usage / Cost
```

App Shell은 메뉴, 공통 탐색, 인증/설정 진입, 모듈 실행과 연결만 담당한다. 각 모듈의 핵심 처리 로직과 도메인 상태를 App Shell이 직접 소유하지 않는다.

## 2. Standalone-first

새 모듈은 업무수첩의 다른 기능이 없어도 핵심 사용가치가 있어야 한다.

기본 흐름은 다음을 권장한다.

`Input → Core Processing → Result → Save / Export / Share → Optional Connections`

### 스캐너 예시

`사진/갤러리 → 자르기/보정 → 여러 장 관리 → PDF → 저장/공유 → 필요하면 업무기록에 첨부`

OCR은 스캐너의 필수 전제가 아니라 선택적 Processor다.

### 통화정리 예시

`녹음 선택 → STT → 녹취록 → 통화 보고서 → 저장/공유 → 필요하면 업무/일정/CRM 연결`

Notion 저장이나 일정 추출이 실패해도 통화 보고서 자체를 사용할 수 있어야 한다.

### 회의정리 예시

`녹음 → STT → 회의록 → 저장/공유 → 필요하면 참석자/업무/일정 연결`

## 3. 모듈의 최소 구성

새 모듈은 가능한 한 아래 책임을 분리한다.

### Input

사용자가 모듈에 넣는 원본 또는 안전한 메타데이터를 받는다.

예: 이미지, 녹음 선택, 캡처, 메일 참조, 직접 입력.

### Domain State

모듈 내부에서 사용하는 상태와 식별자를 소유한다. 다른 모듈이 DOM이나 내부 변수에서 상태를 긁어오지 않게 한다.

### Core Processor

모듈 자체 기능을 수행한다.

예: PDF 생성, 녹취 정규화, 보고서 생성, 일정 후보 추출.

외부 공급자가 필요한 경우 Processor 내부에 특정 공급자 코드를 직접 퍼뜨리지 않고 Adapter를 사용한다.

### Result Model

모듈이 만들어낸 결과를 업무수첩 내부 표준 데이터로 표현한다.

예: `ScanDocument`, `CallReport`, `MeetingReport`, `ScheduleCandidate`.

외부 서비스의 필드명이나 속성명을 Result Model의 기준으로 사용하지 않는다.

### Module UI

해당 모듈의 입력, 진행상태, 결과 검수, 저장/공유까지 자체적으로 처리할 수 있어야 한다.

### Optional Connections

업무기록, 일정, CRM, 브리핑, 외부 공유 등은 핵심 결과가 완성된 뒤 선택적으로 연결한다.

## 4. 모듈로 인정하는 완료조건

새 기능은 아래 항목을 가능한 범위에서 만족해야 한다.

1. 다른 모듈을 열지 않아도 핵심 흐름을 시작할 수 있다.
2. 핵심 결과를 다른 모듈 없이 확인할 수 있다.
3. Notion이나 특정 외부 저장소가 없어도 핵심 처리 결과가 사라지지 않는다.
4. 외부 서비스 실패가 해당 모듈의 이미 생성된 결과를 파괴하지 않는다.
5. 다른 모듈의 DOM, 전역 변수, 내부 저장구조를 직접 읽지 않는다.
6. 모듈 간 연결은 명시적 이벤트, 함수 계약, Adapter 또는 표준 데이터 객체를 사용한다.
7. 외부 공급자 교체가 Module UI와 핵심 도메인 로직의 대규모 수정으로 이어지지 않는다.
8. 모듈 단독 테스트와 App Shell 연결 테스트를 구분할 수 있다.

모든 항목을 기계적으로 강제하는 것이 목적은 아니지만, 새 기능 설계 리뷰의 기본 체크리스트로 사용한다.

## 5. 데이터 소유권

### 모듈은 자기 도메인 상태를 소유한다

통화 모듈의 선택 통화, 녹취, 보고서는 통화 모듈이 소유한다. 스캔 모듈의 페이지와 PDF 상태는 스캔 모듈이 소유한다.

App Shell이나 다른 모듈이 이를 DOM 스크래핑으로 복원하는 구조를 만들지 않는다.

### App Shell은 연결 상태만 소유한다

App Shell은 어떤 모듈이 열려 있는지, 공통 메뉴/설정, 모듈 간 이동과 명시적 전달을 관리한다.

### 외부 저장소는 내부 도메인 모델의 원본이 아니다

Notion, Supabase, Kakao, Calendar 등의 스키마는 Adapter에서 다룬다.

예:

```text
CallReport
   ↓
Worklog Adapter
   ↓
Notion
```

```text
ScheduleCandidate
   ↓
Schedule Adapter
   ↓
업무수첩 일정 / 외부 Calendar
```

## 6. Adapter / Service 원칙

Adapter는 교체 가능한 외부 경계를 담당한다.

### 대표 Adapter

- Worklog / Notion Adapter
- Schedule Adapter
- CRM Adapter
- Storage Adapter
- STT Adapter
- AI Adapter
- Kakao Adapter
- Calendar Adapter

### Adapter 규칙

- 비밀값은 모듈 클라이언트 코드에 넣지 않는다.
- 공급자 전용 오류/응답을 내부 표준 형태로 정규화한다.
- 외부 API 응답을 그대로 Module UI의 상태로 사용하지 않는다.
- 유료 처리에는 비용 게이트와 usage 기록을 둔다.
- 대용량 파일은 불필요하게 Netlify Function 본문을 경유시키지 않고 적절한 Storage 경계를 사용한다.
- 외부 서비스 실패 시 재시도와 중복처리 방지를 고려한다.

## 7. 모듈 간 통신

### 권장

- 명시적 함수 계약
- 표준 이벤트 + 명시적 payload
- 내부 표준 데이터 객체
- Adapter를 통한 저장/전달

### 지양

- 다른 화면 DOM에서 값을 다시 긁어오기
- 다른 모듈의 private 상태를 직접 변경
- 여러 모듈이 같은 상태를 동시에 소유
- 특정 Notion 속성명을 도메인 코드 곳곳에서 직접 사용
- 특정 STT/AI 공급자 응답 형식을 화면 코드 전체에 노출
- App Shell에 모든 모듈의 업무 규칙을 누적

## 8. 결과와 연결을 분리한다

핵심 결과와 업무 연결은 같은 성공 조건이 아니다.

예를 들어 통화정리에서는:

1. STT가 성공해 녹취록을 만든다.
2. 보고서를 만든다.
3. 사용자가 보고서를 확인한다.
4. 선택적으로 업무/일정/CRM에 보낸다.

4번이 실패해도 1~3의 결과를 잃으면 안 된다.

스캐너에서도 PDF 생성이 성공했다면 OCR이나 업무첨부 실패 때문에 PDF를 잃으면 안 된다.

## 9. 현재 데이터 계층의 역할

### 사용자 기기

음성·사진 등 원본의 기본 위치다. 명시적 처리 전에는 서버 업로드를 전제로 하지 않는다.

### Notion

현재 사람이 읽는 실제 업무기록의 기본 원장이다.

다만 도메인 모듈은 Notion schema에 직접 결합하지 않고 Worklog/Notion Adapter를 거친다.

### Supabase 등 앱 DB

향후 처리 job, 내부 ID, 관계, usage, retry, 시스템 메타데이터를 담당할 내부 엔진 후보이다.

기존 다른 프로젝트의 DB를 업무수첩용으로 재사용한다고 가정하지 않는다. 업무수첩 전용 저장소를 실제로 만들거나 변경할 때는 별도 설계와 승인이 필요하다.

### Netlify

PWA 정적 배포, API/Function, 예약 실행과 외부 서비스 중계를 담당한다. 업무 원본의 장기 저장소로 보지 않는다.

## 10. 점진적 이행

현재 코드 전체를 모듈 구조로 한 번에 재작성하지 않는다.

### 새 기능

새 기능은 가능하면 처음부터 이 문서의 모듈 경계를 따른다.

### 기존 기능

기존 기능은 다음 상황에서만 안전한 범위로 개선한다.

- 기능 확장으로 기존 결합이 실제 장애물이 될 때
- 사용자 발견 버그를 고치면서 경계를 함께 개선할 수 있을 때
- 다른 모듈에서 재사용해야 할 계약이 생겼을 때
- 외부 공급자를 교체하거나 새 Adapter가 필요할 때

정상 동작 중인 기능을 단지 디렉터리 구조를 예쁘게 만들기 위해 재작성하지 않는다.

## 11. PWA와 네이티브

모듈의 Result Model과 Adapter 경계를 브라우저 DOM에 종속시키지 않는다.

PWA에서 가능한 기능을 우선 완성하고, Android의 파일/공유/카메라/통화/기기 ML 같은 네이티브 기능이 분명한 이득을 줄 때 같은 모듈 계약 위에 native bridge 또는 app shell을 추가한다.

즉 미래의 네이티브 앱은 제품을 다시 만드는 프로젝트가 아니라, 가능한 한 기존 모듈을 다른 실행환경에 연결하는 확장으로 본다.

## 12. 신규 모듈 개발 순서

권장 순서는 다음과 같다.

1. 독립 사용자 문제 정의
2. 독립 핵심 흐름 정의
3. Result Model 정의
4. 자체 UI와 상태 구현
5. 단독 테스트/Preview 검수
6. 외부 Adapter 연결
7. 업무수첩 App Shell에 진입점 연결
8. 업무기록/일정/CRM 등 선택적 연결
9. 통합 회귀검사

이 순서를 통해 업무수첩 자체가 각 기능 개발의 테스트 환경이 되는 것을 피한다.

## 13. 현재 우선 적용 대상

### 통화정리

현재 진행 중인 통화 기능은 첫 번째 표준 모듈 사례로 본다.

핵심 독립 완료선은:

`통화녹음 선택 → STT → 전체 녹취 → 통화 보고서 → 검수 → 자체 결과 보존/공유`

그 이후 업무, 일정, CRM 연결은 선택적 Adapter 단계다.

### 문서 스캔/PDF

두 번째 표준 모듈 사례로 본다.

핵심 독립 완료선은:

`카메라/갤러리 → 페이지 보정 → 여러 장 관리 → PDF → 저장/공유`

OCR과 업무기록 첨부는 선택적 확장이다.

## 한 줄 기준

> **독립적으로 유용하지 않은 기능을 App Shell에 먼저 얽지 말고, 독립 결과를 만든 뒤 표준 계약으로 연결한다.**
