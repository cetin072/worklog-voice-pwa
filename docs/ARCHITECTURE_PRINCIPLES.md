# 업무수첩 Core & Branch 개발 헌법

이 문서는 업무수첩의 기능 수보다 **빠름, 단순함, 직관성, 안정성**을 지키기 위한 상위 설계 원칙이다.

일반 작업마다 이 문서 전체를 다시 읽는 체크리스트로 사용하지 않는다. 신규 핵심 기능, 외부 연동, 데이터 경계, 아키텍처 변경처럼 구조 판단이 필요한 작업에서만 참조한다. 일상적인 버그·문구·스타일 수정은 AGENTS.md와 해당 Issue/인접 코드만으로 충분하다.

## 1. 단일 Source of Truth

- 핵심 데이터의 주인은 하나만 둔다.
- 업무는 WorkRecord, 일정은 Schedule처럼 canonical Core를 명확히 한다.
- 외부 서비스나 UI 로컬 상태를 별도의 진실 원천으로 만들지 않는다.

## 2. 한 번에 하나

- 새 기능은 가장 작은 유용한 V1부터 완성한다.
- V1이 자동검증과 필요한 Human QA를 통과하기 전에 V2 기능을 섞지 않는다.
- 미래 가능성만으로 설정, 상태, 테이블, 네트워크 경로를 미리 만들지 않는다.

## 3. Core는 안정시키고 기능은 Branch로 붙인다

- 검증된 Core를 새 기능 때문에 반복해서 뜯지 않는다.
- 신규 기능은 가능한 한 좁은 Contract/Coordinator/Adapter 경계로 연결한다.
- 새 기능 때문에 여러 기존 Core가 동시에 수정되어야 한다면 먼저 경계가 잘못됐는지 확인한다.

## 4. 입력과 출력을 분리한다

- Quick Voice, 직접입력, 회의, 통화, 캡처, 메일은 입력 수단이다.
- Reminder, Calendar Sync, 보고서, 외부 전송은 출력/후속처리다.
- 입력 기능이 Reminder나 Calendar provider를 직접 제어하지 않는다.
- 모든 입력은 canonical Work/Schedule까지만 책임지고 후속 기능은 그 확정 결과를 소비한다.

## 5. 외부 서비스는 선택적 Adapter다

- Google Calendar, Samsung/Apple Calendar, Notion, Firebase, STT/OCR/AI provider가 없어도 핵심 업무수첩은 가능한 범위에서 정상 작동해야 한다.
- 외부 서비스는 Core의 Source of Truth가 되지 않는다.
- provider 교체가 UI·DB·업무규칙 재작성으로 이어지지 않도록 기존 Adapter 원칙을 따른다.

## 6. 복잡성 예산

- 기존 모듈로 해결할 수 있으면 새 시스템을 만들지 않는다.
- 새 dependency, DB table, 상태 저장소, background job, 네트워크 경로는 명확한 필요가 있을 때만 추가한다.
- 코드 추가보다 기존 안정된 경계 재사용을 우선한다.
- 줄 수를 줄이는 것 자체가 목적은 아니다. 이해 가능한 단순성이 목적이다.

## 7. 새 아이디어는 먼저 연결 위치를 정한다

구현 전에 다음 세 질문에 답한다.

1. 이 기능은 어느 Core의 입력/출력 Branch인가?
2. 가장 작은 유용한 V1은 무엇인가?
3. 기존 Core를 바꿔야 하는가, 아니면 기존 Contract에 연결할 수 있는가?

답이 불명확하면 구현 범위를 확대하지 말고 먼저 구조를 확인한다.

## 8. 큰 기능 전 구조 감사

- 여러 모듈, 데이터 모델, 외부 서비스에 걸치는 기능 전에는 현재 결합·중복·책임 경계를 확인한다.
- 구조 감사 결과가 있어도 미학적 대규모 리팩터링을 자동으로 시작하지 않는다.
- 실제 신규 기능을 막는 P0와 작은 비용으로 큰 효과가 있는 P1만 우선한다.

## 9. 검증된 Core는 KEEP이 기본값

- 자동검증과 Human QA를 통과한 핵심 경로는 재사용을 기본으로 한다.
- 재작성은 구체적인 결함이나 요구사항이 기존 경계로 해결되지 않을 때만 한다.
- 변경 시 영향범위와 회귀검증을 명시한다.

## 10. 제품 기준

우선순위는 기능 개수가 아니다.

**빠름 → 단순함 → 직관성 → 안정성 → 확장성**

확장성은 미래 기능을 미리 구현하는 것이 아니라, 현재 Core를 명확하게 만들어 다음 Branch를 작게 붙일 수 있게 하는 것이다.

## 예시: Schedule 중심 확장

```text
Quick Voice ─┐
직접입력 ────┤
회의/통화 ───┼→ Work / Schedule ─┬→ Reminder
캡처/메일 ───┘                   ├→ Calendar Sync
                                  └→ 기타 후속 기능
```

각 입력은 Reminder/Calendar를 직접 알지 않는다. Reminder와 Calendar Sync도 서로를 소유하지 않는다. 모두 확정된 canonical Schedule을 소비한다.

## 작업 중 충돌 시

이 원칙과 기존 구현이 충돌한다고 해서 즉시 대규모 재작성하지 않는다.

- 현재 기능을 보존한다.
- 충돌 지점을 Issue/PR에 명시한다.
- 최소 변경안과 별도 정비안을 구분한다.
- 범위 확대가 필요하면 사용자 승인 전 구현을 확대하지 않는다.
